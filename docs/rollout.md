# Сборка и выкладка

`rollout` собирает выбранные компоненты на ПК и публикует результат в обычный
каталог или уже смонтированную SD. Приложения не запускаются, NOR не меняется.
Подготовка карты — отдельная [разрушительная операция](card.md).

## Платформы и зависимости

Iroll работает на 64-разрядном Linux x86-64. Платформы сборки:

- `linux-x86_64` — приложения для ПК, значение по умолчанию;
- `rk3032` — приложения для стика, с заранее подготовленным [SDK](sdk.md).

Набор инструментов зависит от компонентов: C/C++-компиляторы, Make,
`pkg-config`, Rust 1.85 или новее и стандартная библиотека выбранной цели Rust.
Для RetroArch на ПК нужны библиотеки X11, OpenGL, udev, PulseAudio и zlib.
`deps` проверяет зависимости и рекомендует установку, но ничего не устанавливает;
в Ubuntu/Debian выводится команда для недостающих системных пакетов.

## Рабочая директория

Все относительные пути считаются от текущего рабочего каталога,
не от установленного пакета и не от `--source`.

```text
./
├── in/
│   ├── components/{igui,iman}/           # Локальные проекты или ссылки на них.
│   ├── downloads/                       # Закреплённые архивы компонентов.
│   │   └── sdk/rk3032/                  # Архивы подготовки SDK.
│   ├── sdk/rk3032/                      # Готовый SDK.
│   └── bios/<PLATFORM>/                 # BIOS владельца, необязательные.
├── out/                                # Готовый комплект.
├── tmp/
│   ├── build/
│   │   ├── our/<platform>/              # Cargo target-dir.
│   │   └── their/
│   │       ├── src/<name>/              # Одна текущая распаковка на компонент.
│   │       ├── src/<name>.json           # Состояние успешной распаковки.
│   │       └── compiled/<platform>/<name>/
│   └── out_stage/                      # Бинарники и ресурсы до публикации.
└── logs/<command>/<run>/                # Журналы и отчёты ПК.
```

Подготовьте проекты [IGUI](https://github.com/idleboxed/igui) и
[iman](https://github.com/idleboxed/iman) заранее. Их каталоги в `in/components/`
могут быть абсолютными или относительными симлинками; зависимости Cargo
разрешаются относительно настоящих проектов. Сам `in/components/` и корни
загрузок, назначения, рабочих данных и отчётов не должны быть симлинками.
Пустые SDK и проекты iroll не создаёт; результаты и рабочие каталоги создаются
по мере необходимости.

| Параметр | Значение по умолчанию |
| --- | --- |
| `--source` | `in/components` |
| `--dest` | `out`, корень комплекта, не его `system/` |
| `--bios` | `in/bios` |
| `--downloads` | `in/downloads` |
| `--build-dir` | `tmp`, корень для `build/` и `out_stage/` |
| `--logs_dir` | `logs` |
| `--jobs` | `4`, допустимо от 1 до 256 |

Параметры путей независимы. Пересечения корней загрузок, сборки, отчётов
и назначения запрещены. Исключение: отчёты могут находиться внутри рабочего
корня, но не в его `build/` и `out_stage/`.
Для Make-сборок `--build-dir` допускает только ASCII-буквы, цифры и `_./+-`:
пробелы и shell/Make-метасимволы небезопасны для штатных Makefile.
Каталоги загрузок, сборки и отчётов блокируются на время операции,
без файлов блокировок на SD.

## Выбор компонентов

```bash
iroll list
iroll deps
iroll rollout
```

`list` показывает доступные компоненты; `deps` проверяет готовность;
`rollout` — единственная команда сборки и публикации приложений.
Без селекторов выбираются IGUI, iman, RetroArch и все доступные ядра:
шесть для ПК, семь для RK3032. Список — в [руководстве эмуляции](emulation.md#ядра-эмуляции).
Несколько селекторов объединяются:

```bash
iroll rollout --with-igui --with-iman
iroll rollout --with-retro --with-cores
iroll rollout --with-core-nestopia
iroll rollout --with-core-picodrive --dest /path/to/output
```

`--with-cores` выбирает ядра, не RetroArch: при необходимости добавьте `--with-retro`.
`--with-itrampoline` отдельно выбирает трамплин для RK3032; без этого селектора
его нет в обычном полном наборе. Подготовьте также checkout
[itrampoline](https://github.com/idleboxed/itrampoline) в `--source/itrampoline`:
сборщик использует именно этот исходный пакет, а не глобально установленную версию.
Helper выкладывается в `system/itrampoline`, core сохраняется только в отчётах ПК
как `itrampoline_libretro.so`; его путь указан в `components.itrampoline.artifacts`
отчёта `result.json`. Штатное ядро и `game/games.db` не меняются.
Для встраивания следуйте [инструкции itrampoline](https://github.com/idleboxed/itrampoline/blob/main/docs/usage.md).

Селекторы также доступны у `deps`. Для RK3032 передавайте платформу явно:

```bash
iroll list --platform rk3032
iroll deps --platform rk3032
iroll rollout --platform rk3032 --dest /path/to/card
```

SDK по умолчанию ищется в `in/sdk/rk3032/`; другой корень выбирается через `--sdk`.
`rollout` сам `sdk prepare` не запускает. Сборка и выкладка выполняются
от обычного пользователя; команда не монтирует SD и не проверяет, что назначение
действительно является картой. Проверьте точку монтирования самостоятельно.

Для RK3032 IGUI собирается с `drm,rgb565`, iman — с `drm,diagnostics`.
Пассивные диагностические сборщики и экспорт включаются составом Cargo features,
не runtime-флагами. Для обновления только iman без этих сборщиков:

```bash
iroll rollout --platform rk3032 --with-iman --no-diag --dest /path/to/card
```

`--no-diag` сохраняет release-оптимизацию, RGB565, DRM и обычные сообщения об ошибках.
Он не выбирает iman автоматически и не меняет установленный ELF, если iman
не выбран или замена отклонена через `--ask`. На ПК диагностика уже выключена;
IGUI, RetroArch и ядра от флага не зависят. Для возврата диагностики пересоберите
iman без него.

## Результат

```text
DEST/
├── system/
│   ├── iman/{iman,iman.json,emulation.json}
│   ├── igui/{igui,locales/,controls/}
│   ├── retroarch/{retroarch,cores/,padconf/,shaders/}
│   └── bios/<PLATFORM>/
├── games/{states/,saves/}
└── INSTRUCTIONS.md
```

Состав зависит от выбранных и уже установленных компонентов. При наличии
RetroArch формируется `system/iman/emulation.json`; пути в нём относительны
`system/`, не папке JSON. `settings` при каждой полной или частичной выкладке
заново берётся из профиля платформы: ручные прежние значения не объединяются
с defaults. [BIOS, геймпады и остальные профили](emulation.md).

Готовые ресурсы пакета собраны в [дереве `resources/sd/`](development.md#ресурсы).
Выкладка выбирает их явно по платформе и компонентам, не копирует дерево целиком.

При выборе IGUI копируются локализации и все непосредственные `controls/*.json`
из проекта. Нужен хотя бы один JSON; обязательных имён и моделей нет.
Содержимое, размеры и конфликты профилей проверяет IGUI при старте, не iroll.
Удалённые или переименованные во входах JSON не удаляются из назначения;
старый профиль может конфликтовать с новым. Правка JSON требует перезапуска IGUI,
не пересборки бинарника.

Любая выкладка готовит `games/states/` и `games/saves/` без изменения содержимого.
Старые корневые `states/` и `saves/` не переносятся автоматически.
На SD не создаются `iroll.json`, `.iroll.lock`, `licenses/`, `releases/`
и маркеры `BOX2-ALLOW.txt`/`BOX2-EXPORT.txt`; старые файлы не удаляются.
Лицензии исходников и обязательства распространения компонентов сохраняются;
происхождение сборок записывается в отчётах ПК, не в дополнительном SD-инвентаре.

## Публикация и отмена

Все выбранные компоненты сначала собираются и проверяются вне назначения.
Новые файлы устанавливаются; одинаковые не перезаписываются; изменённые
поставляемые файлы заменяются по умолчанию. Невыбранные компоненты и посторонние
данные, включая `prefs.json`, `games/catalogue.json`, ROM и сохранения, не меняются.

Для подтверждения каждой замены существующего файла:

```bash
iroll rollout --ask --dest /path/to/card
```

Нужен интерактивный терминал. `y` или `Y` разрешает замену; Enter и любой
другой ответ сохраняют прежний файл. Новые файлы устанавливаются без вопроса,
одинаковые пропускаются. Все вопросы задаются до публикации; Ctrl+C на этом
этапе отменяет её. Вопросы идут в stderr, поэтому `--ask --json` не загрязняет stdout.
Сохранённые по отказу файлы перечисляются в `kept_files` отчёта.
Отказ для `emulation.json` сохраняет весь манифест, не отдельные настройки;
совместимость смеси старых и новых компонентов не гарантируется.

Симлинки в устанавливаемых путях, конфликты файла с каталогом, нехватка места
и внешнее изменение назначения вызывают отказ. Изменённые файлы синхронизируются
и заменяются по одному, манифест эмуляции — последним.
Это **не атомарная транзакция всего комплекта**: ошибка или отключение питания
могут оставить частичную выкладку, автоматического отката нет.
Приложения перед обновлением нужно остановить, SD после успешной записи —
корректно размонтировать.

Незавершённые `.iroll-stage-*` и `.iroll-backup-*` в назначении сохраняются
для ручного разбора и блокируют следующую публикацию. Не удаляйте их и не
повторяйте операцию до проверки отчёта и отсутствия работающего iroll.

## Загрузки и кеш сборки

Архивы компонентов закреплены URL, commit и SHA-256 в
[`registry.py`](../src/iroll/components/registry.py). Недостающие скачиваются;
отдельного offline-флага нет. Архивы SDK находятся отдельно в `sdk/rk3032/`
под корнем загрузок.

Для каждого стороннего компонента сохраняется одна текущая распаковка,
общая для платформ. Перед повторным использованием состав, содержимое и права
сверяются с архивами. Изменённое дерево с действующим состоянием отклоняется,
не исправляется молча. При смене архива или незавершённой распаковке тот же
каталог пересоздаётся. Сторонние исходники и Makefile не патчатся.

Сборочное дерево `compiled/` содержит каталоги и ссылки на исходные файлы;
объекты, конфигурация и новые заголовки создаются только там. Make линкует
сразу в `out_stage/system/`, Cargo копирует результат туда, сохраняя свой кеш.
Состояние успешной Make-сборки `.iroll-build.json` учитывает архивы, подмодули,
рецепт, профиль, окружение и содержимое toolchain/SDK; для PicoDrive учитывается
также нативный генератор Cyclone. Копии toolchain не создаются.

При совпадении входов `configure` пропускается, Make переиспользует объекты
и перелинковывает результат в свежий staging. При смене входов или отсутствии
состояния успеха пересоздаётся только выбранный каталог компонента/платформы.
Число `--jobs` и назначение не меняют ключ кеша. Логи показывают
`Reusing compiled files` или причины `Build cache miss`.

Make, `configure` и пробы toolchain получают явное окружение профиля.
Из окружения пользователя сохраняются только `PATH`, `HOME`, `TMPDIR`
и `SOURCE_DATE_EPOCH`, если заданы; они учитываются в ключе.
Остальные переменные не передаются, поэтому внешние `CFLAGS`, `MAKEFILES`
или `LD_PRELOAD` не меняют эти сборки. Политика Cargo и подготовки SDK отдельная.
Не изменяйте кеш или SDK во время сборки; автоматической миграции старых путей нет.

`out_stage/` удаляется при успехе, обработанной ошибке и отмене. Аварийный остаток
блокирует следующий запуск: его нужно проверить и удалить вручную при отсутствии
работающих процессов. Неполный комплект не переиспользуется и не публикуется автоматически.

## Отчёты и вывод

Журналы и отчёты находятся в `<logs_dir>/<command>/<run>/`.
Имена команд: `sdk-prepare`, `card-init`, `card-deps`, `rollout`, `deps`, `list`.
Имя запуска — UTC `YYYY-MM-DDTHH:MM:SSZ`; при совпадении секунды добавляется
`_01`, затем `_02`. Отчёты остаются после завершения операции.

Рабочие команды поддерживают `--json`: данные идут в stdout, диагностика —
в stderr. `--verbose` включает подробную диагностику. Коды завершения:

| Код | Значение |
| --- | --- |
| `0` | Успех |
| `1` | Ожидаемая ошибка или отсутствующая зависимость |
| `2` | Неверные аргументы |
| `130` | Прерывание |
