# Профили эмуляции

Iroll собирает RetroArch и ядра, выкладывает ресурсы и формирует
`system/iman/emulation.json`. Запуск игр, временные файлы и применение настроек —
ответственность совместимого iman и RetroArch.
Обновляйте iman, манифест и ресурсы согласованно: старый менеджер может игнорировать
новые поля. Наличие рецепта не подтверждает совместимость всех игр, периферии
или производительность на RK3032.

## Ядра эмуляции

Шесть общих рецептов доступны для ПК и RK3032; N64 — только для RK3032.

| Селектор | Ядро | Платформы манифеста |
| --- | --- | --- |
| `--with-core-nestopia` | Nestopia | `NES`, `FDS` |
| `--with-core-gambatte` | Gambatte | `GB`, `GBC` |
| `--with-core-snes9x2010` | Snes9x 2010 | `SNES` |
| `--with-core-gpsp` | gpSP | `GBA` |
| `--with-core-picodrive` | PicoDrive | `MD`, `SMS`, `GG`, `SG1000`, `SC3000`, `SCD`, `32X`, `PICO` |
| `--with-core-pcsx-rearmed` | PCSX ReARMed | `PSX` |
| `--with-cores` или полный комплект, только `rk3032` | Mupen64Plus-Next | `N64` |

`SCD` — Sega/Mega CD, `PSX` — первая PlayStation.
Рецепты и SHA архивов закреплены в [`registry.py`](../src/iroll/components/registry.py).
У N64 отдельного CLI-селектора нет; `list --json` показывает `flag: null`.

PicoDrive — единственное Sega-ядро новых сборок. При его выкладке `MD` назначается
ему; старый ELF Genesis Plus GX автоматически не удаляется.
Save states разных ядер нельзя считать совместимыми.
Snes9x 2010 выбран для слабых устройств по исходникам и возможностям,
не по сравнительному измерению FPS на RK3032; Beetle-ядра не включены.

Для ARM gpSP использует ARM dynarec, PCSX ReARMed — `ari64` и NEON GPU,
а Snes9x 2010 явно линкуется с pthread для glibc 2.29.
PicoDrive собирается с закреплёнными подмодулями без патчей upstream;
генератору Cyclone нужны также нативные `cc` и `c++` на ПК.

Игровой каталог готовится отдельно с [icat](https://github.com/idleboxed/icat).
Поддерживаются только самодостаточные однофайловые игровые образы;
CUE с внешними дорожками и M3U с отдельными дисками не входят в контракт.
ZIP/7z — упаковка для извлечения на ПК, не runtime-носитель.
Поддержка формата ядром сама по себе не добавляет импорт, переключение дисков
или проверенный запуск через iman.

## Настройки RetroArch

[`emulation-linux-x86_64.json`](../src/iroll/emulation/emulation-linux-x86_64.json)
и [`emulation-rk3032.json`](../src/iroll/emulation/emulation-rk3032.json) задают
`settings`. При любой полной или частичной выкладке этот объект формируется
заново; прежние ручные значения не объединяются с defaults.
`--ask` позволяет сохранить весь прежний манифест.

RK3032 использует ALSA с `audio_latency: 232`, KMS/GLES и threaded video,
без автоматической смены HDMI-частоты; ПК — PulseAudio и оконный вывод.
Выбор профиля не доказывает отсутствие аудиоошибок или достаточную скорость игр.
Смена параметров применяется через новый манифест без пересборки RetroArch.

Быстрое меню открывается комбинацией Start+Select. Скрыты Add to Favorites,
Latency, Rewind, Overrides и Cheats; Shaders, Information, Core Options,
сохранение/загрузка состояния, снимок экрана и выход остаются доступны.
Избранное IGUI не затрагивается. Общий frontend-турбо отключён через
`input_turbo_enable=false`; отдельное X/Y-турбо Nestopia сохраняется для NES.
Автосохранение конфигурации/remap, истории и состояний выключено.

## BIOS

BIOS предоставляет владелец: iroll не скачивает их, не извлекает из ROM и не
включает в дистрибутивы. Любой `rollout`, включая частичный, читает
`in/bios/<PLATFORM>/<file>` и выкладывает в `system/bios/<PLATFORM>/<file>`.
`--bios DIR` меняет только корень входов, независимо от `--source` и `--dest`.
Одинаковые файлы пропускаются; замены используют общий механизм `--ask`.
Отсутствующие во входе файлы не удаляются из назначения; отсутствие `in/bios/`
допустимо и не блокирует сборку приложений.

Идентификаторы платформ — заглавные ASCII-буквы, цифры, `_` и `-`, до 64 символов.
Разрешены обычные файлы и вложенные каталоги; симлинки, hardlink и специальные
файлы запрещены. Пустые каталоги не выкладываются. Файлы повторно сверяются
после компиляции; изменение отменяет публикацию. SHA записываются в отчёте ПК.
Общий предел одного артефакта — 256 МиБ; отдельного лимита копирования BIOS в RAM нет.

FDS/Nestopia требует `FDS/disksys.rom` размером 8192 байта: сырой BIOS,
не переименованный iNES-картридж. Для PSX и Sega CD используйте соответственно
`PSX/` и `SCD/`; необходимые файлы и содержимое определяет ядро, не iroll.
Для уже поддержанной платформы добавление BIOS не требует изменения манифеста
или пересборки iman.

Обычно iman передаёт каталог выбранной платформы как `system_directory`:
ядро читает его прямо с SD, не из RAM-копии. Без BIOS-каталога используется
пустой каталог runtime в RAM, без создания папки на SD и без fallback к ROM.
Это не отдельное RO-монтирование: при SD в RW ядро технически может писать туда.
N64 использует отдельную RAM-политику, описанную ниже.

## Управление

При наличии RetroArch любая выкладка публикует четыре профиля в
`system/retroarch/padconf/`: для `0810:0001`, `20bc:5500`, `045e:028e` и `0079:181c`.
RetroArch выбирает их по точному имени и VID/PID; iman задаёт вычисленный путь
к этому каталогу. Профили IGUI из `controls/` не управляют игровыми кнопками.

У `20bc:5500` дополнительный EV_KEY 107 (Mode) сдвигает последующие индексы
RetroArch относительно `0810:0001`. Поэтому одинаковый внешний вид падов
не позволяет использовать один набор физических номеров.
В этих двух autoconfig назначены D-pad, лицевые кнопки, Select/Start, L1/R1 и L2/R2;
L3/R3, Mode и оси не назначены.
Это данные измерений двух профилей, не универсальная раскладка любого контроллера.

`045e:028e` с именем `Microsoft X-Box 360 pad` использует крестовину HAT0,
оба грибка, аналоговые LT/RT, LB/RB, L3/R3, Back/Start и Guide.
`0079:181c` с именем `ShanWan Wireless Gamepad` использует оба грибка,
цифровые LT/RT, LB/RB, L3/R3, Back/Start и Guide. Его левый грибок также
назначен направлениям RetroPad вместо крестовины; сама крестовина не назначена.
Лицевые кнопки в обоих профилях сопоставлены по положению, как в RetroPad:
нижняя — B, правая — A, левая — Y, верхняя — X.
Номера осей и кнопок в CFG — индексы RetroArch, не evdev-коды из JSON IGUI.

[`emulation-cores.json`](../src/iroll/emulation/emulation-cores.json) задаёт
логические remap и core options для точных пар бинарник/платформа, одинаково
для ПК и RK3032. Для первых двух портов сохраняются кнопки выбранного
оригинального контроллера; добавленные функции эмулятора отключаются значением `-1`.
Исключения — согласованные назначения FDS-дисков и пера/страниц PICO.

| Платформы | Назначения и ограничения |
| --- | --- |
| NES | A/B по буквам, X/Y — Turbo A/B выбранного турбо-пада; плечи отключены |
| FDS | A/B; X/Y первого порта — сторона/диск, второго — Turbo A/B; плечи отключены |
| GB/GBC | A/B, Start/Select, D-pad; турбо, fast-forward и смена палитры отключены |
| GBA | A/B, L/R, Start/Select, D-pad; турбо и fast-forward отключены |
| SNES | A/B/X/Y, L/R, Start/Select, D-pad; L2/R2/L3/R3 отключены |
| MD/SCD/32X | Шестикнопочный пад A/B/C/X/Y/Z, Start/Mode; L2/R2/L3/R3 отключены |
| SMS/GG | Кнопки 1/2, D-pad, Start — Pause/Start; Select, X/Y и плечи отключены |
| SG1000/SC3000 | Двухкнопочный джойстик; Start/Select, X/Y и плечи отключены |
| PICO | Цветные направления, Red/Pen; режимы пера и страниц на X/Y/Start/L/R |
| PSX | Cross/Circle/Square/Triangle, плечи, Start/Select; X/Y переставлены |
| N64 | A/B, четыре C-кнопки, Z/L/R, Start; C Buttons Mode и правый стик-дубль отключены |

Для MD/SCD/32X физические Y/A/B соответствуют Sega A/B/C, L1/X/R1 — X/Y/Z,
Select — Mode. Для N64 физические A/Y соответствуют A/B, B/X/L1/R1 —
C-Down/Up/Left/Right, L2 — Z, R2 — R, Select — L.
Аналоговые каналы Control Stick/DualShock не блокируются основным remap,
но в двух поставляемых autoconfig осей нет: их работа не подтверждается этим профилем.
Клавиатура SC3000, световые пистолеты, микрофоны и многопортовые адаптеры не интегрированы.

Поставляемые defaults заново применяются и при частичных обновлениях точной пары;
для другого явно назначенного ядра они не применяются.
Отдельные `.rmp` на SD не выкладываются: совместимый iman создаёт их в RAM.
Отказ от замены манифеста сохраняет прежние назначения целиком.
Пересборка ядра или RetroArch для смены remap и pad CFG не нужна.

## N64

Mupen64Plus-Next закреплён на commit
`12edd2c74a517ff86dfa8cfc71ad75e4c10486d5`. ARM-рецепт выбирает Cortex-A7,
NEON hard-float, ARM dynarec, GLES2/GLideN64 и HLE RSP, без Vulkan/GLES3/LLE.
Генерации ASM нужны штатные `awk`, `strings` и `tr` на ПК; upstream и SDK не патчатся.

Профиль задаёт 4:3/320×240, отключает high-resolution packs и дисковые texture caches.
`mupen64plus-EnableCopyDepthToRDRAM: "Off"` — экспериментальная настройка
производительности/совместимости, не исправление всех игр; baseline upstream —
`"Software"`. `mupen64plus-alt-map: "True"` относится к управлению, не графике.

`system_directory: "ram"` направляет генерируемый `Mupen64plus/mupen64plus.ini`
и другие системные данные в проверенный tmpfs независимо от `system/bios/N64`.
Core options создаются в RAM. При любом rollout с точной установленной парой
`mupen64plus_next_libretro.so`/`N64` весь её профиль применяется заново:
`core_options` заменяются без объединения ручных ключей, `system_directory`
возвращается к `"ram"`. `--ask` сохраняет только весь старый манифест.
Для этой политики нужен совместимый iman; старый менеджер её не обеспечивает.

EEPROM, Controller Paks, SRAM и FlashRAM обычных картриджей представлены
единым libretro SaveRAM в `<hash>.srm`. 64DD и Transfer Pak не интегрированы;
скорость, память и совместимость всех ROM не гарантируются.

## Шейдеры и пресеты

Для известных пар ядро/платформа поставляется Sharp Bilinear Simple — фильтр
масштабирования без CRT, сканлайнов и LCD-сетки. Общие файлы находятся в
`system/retroarch/shaders/libretro/interpolation/`, используемые пресеты —
в `system/retroarch/shaders/presets/<PLATFORM>.glslp`.
Каждый пресет ссылается на общую upstream-пару через `#reference`.

Источник — [закреплённая ревизия libretro/glsl-shaders](https://github.com/libretro/glsl-shaders/tree/f8e23ff880668f0f0e837a05a316534d82a7f31b/interpolation).
Байты и уведомление Public domain сохранены; ресурсы входят в пакет и не требуют
сети при выкладке. SHA проверяются, происхождение записывается в
`bundled_shader_source` отчёта ПК, не в отдельном SD-инвентаре.

`cores.<PLATFORM>.shader_preset` — путь относительно `system/`; iman передаёт
его через `--set-shader`. Автопоиск по ROM/ядрам выключен.
При частичном обновлении переиспользуемого ядра явный пользовательский путь
или `null` сохраняется; отсутствующее поле получает поставляемый default.
Чтобы сохранить отключение, задавайте `null`, а не удаляйте поле.
Замена ядра заново формирует его настройки; неизвестной паре default не назначается.

Недостающие поставляемые ресурсы восстанавливаются и при частичном rollout
без пересборки RetroArch. `--ask` позволяет оставить изменённые файлы;
старые неиспользуемые и посторонние пресеты не удаляются.
Проверяется главный `.glslp`; цепочки ссылок, GPU-совместимость и производительность
остаются ответственностью RetroArch, не гарантируются iroll.

## Сохранения и записи

Профили обеих платформ задают `autosave_interval: 60`: RetroArch раз в минуту
проверяет SaveRAM/RTC и пишет изменившиеся данные. Совместимый iman использует
`--sram-mode load-save`: загрузка при старте и сохранение при штатном выходе.
Это согласованное исключение из запрета неявных записей, не Save State;
отдельное действие SaveRAM в IGUI не требуется.

Постоянные файлы — `games/saves/<ROM-SHA256>.srm` и, для ядер с RTC, `.rtc`.
Имена привязаны к полному хешу ROM, не его названию. Iman передаёт этот каталог
напрямую, не копирует рабочие данные из RAM после игры.
Снимки состояния находятся отдельно в `games/states/`; их автосохранение
и автозагрузка выключены. Предпочтения IGUI записываются явными действиями пользователя.

**Режим не устойчив к внезапному отключению питания.** Таймер и штатный выход
не подтверждают `fsync`/`syncfs`, атомарную замену или возврат SD в RO.
Можно потерять прогресс после последней успешной записи; ошибки и несброшенный
кеш увеличивают этот период. Обрыв записи может повредить сохранения или файловую систему.
RO с первого монтирования и отдельные интервалы RW → синхронизация → RO
в игровом runtime пока отложены. Подготовка каталогов и малый износ не реализуют эту политику.
